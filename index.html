About

I started as a full-stack developer and I still am one. What has changed is that AI is now part of how I build and ship software, and I've spent the last couple of years working out how to make that reliable.

Most of my experience is in Python with Django and FastAPI, PHP with Laravel, and TypeScript with React, Next.js and Vue. I usually work on PostgreSQL or MySQL and deploy on AWS. On the AI side I've fine-tuned small LLMs with LoRA, built RAG pipelines over company documents, and set up CI pipelines where Claude, Codex and Gemini each review a pull request before it reaches the team. I also write the CLAUDE.md rules, skills and hooks that keep coding agents inside a project's architecture.

I like to test things before I recommend them. I once ran RAG and fine-tuning against the same set of questions. RAG got all ten right and the fine-tuned model did worse, so RAG is what I used.

01

AI-augmented CI/CDArchitect & lead engineer

Multi-LLM code review & QA pipeline

A CI pipeline where Claude, Codex and Gemini each review a pull request. It then tries to fix what they found, runs the Playwright tests and checks the UI, all before anyone on the team opens the PR. A project adds it with about 12 lines of YAML.

Problem

Code review was slowing us down on several client projects. I started with one model as the reviewer, but its results changed from run to run and I didn't trust it enough to block a deploy.

What I built

  • The three models review at the same time. If any one of them asks for changes, the pipeline treats the PR as needing changes.
  • The auto-fix step runs at most twice. Each round fixes, lints, commits and sends the code back for review.
  • A PR uses between 2 and 7 separate agent sessions. Each one gets only the tools it needs, and review sessions are read-only.
  • A script builds the context for each session. It finds the ticket from the branch name, picks the matching skill files, and adds the project rules and the diff.
  • Tests are chosen based on the ticket. When they pass, a narrated demo video is posted on the PR.

02

Developer platformDesign & implementation

Ticket-to-pull-request agent orchestrator

When a ticket gets a certain label, this tool creates a separate git worktree and Docker stack for it and starts a Claude Code session. The agent writes a plan, waits for a person to approve it, then implements it, reviews its own work and pushes a branch.

Problem

Running coding agents by hand works for one developer but not for a team. We needed each ticket to move through clear steps, with a person approving the plan before any code is written.

What I built

  • The ticket's labels hold the state. Hooks in the agent session change the label when a step finishes, and a catch-up query picks up anything missed while the server was down.
  • During planning the agent can't edit code. Editing is switched on only for the implementation step.
  • Three sub-agents review the result for coverage, regressions and scope. They get two rounds at most.
  • It also reads production error alerts from Slack, skips the ones that already have a ticket, and opens a bug with the stack trace attached.
  • Adapters let it work with Jira or Trello, with GitHub, Bitbucket or Azure DevOps, and with Slack.

Agent harnessRegulated industry

Agent guardrails for an environmental-compliance platform

This is a large Laravel application that holds compliance data, and a wrong write can corrupt it. I set up the agent configuration so that the risky actions are blocked by hooks before they run.

Problem

The codebase has more than 130 event listeners, materialised compliance tables and an offline sync layer. An agent that doesn't know this can do damage quickly, and written guidelines alone didn't stop it.

What I built

  • Hooks block raw writes to the materialised tables, stage changes made outside the service that owns them, and any attempt to commit secrets.
  • I wrote 21 sub-agent definitions, about 16 domain skills and 14 sets of path-scoped rules that follow the domain model.
  • CI reads the ticket and its plan, works out which domains are affected from a dependency map, and runs only those Playwright specs.
  • The recordings from that test run are reused for the demo video, so the tests don't have to run twice.

AI-first rewrite of a healthcare diagnostics platform

05

AI data pipelineBackend & platform engineering

Invoice automation with measured LLM extraction

Supplier invoices arrive in a shared mailbox and end up in the accounting system without anyone retyping them. The pipeline saves the PDF, extracts the fields with an LLM, maps the items and exports them. The same data feeds price comparison reports and a chat assistant that answers questions about it.

Problem

Every supplier lays out invoices differently, and a wrong number from the model becomes a wrong number in the books. So the extraction had to be measured.

Engineering highlights

  • A prompt change has to score at least 95 on an extraction scorecard. If field accuracy drops by more than 2%, the change can't be merged.
  • The team keeps 14 architecture decision records and enforces them in review. Routes, controllers and data access are kept separate, and all aggregation is done in SQL.
  • Old code paths were moved over behind feature flags in three phases.
  • The scheduler pauses background jobs while an accounting export runs, to free database connections, and resumes them afterwards.
  • Corrections made by users are stored separately from the dbt marts and applied on top, with an audit log.

Workforce AI assistant: RAG, tools and LoRA

An HR and IT asset platform with a chat assistant. It answers policy questions from a vector store, looks up assets and leave balances, and can open a support ticket during the conversation.

Problem

People kept asking the same policy and asset questions, and the right answer depended on who was asking. The assistant had to respect user roles as well as find the right text.

What I built

Performance engineeringLive consumer platform

Stabilising a platform at 500K+ users

A live platform with more than 500K users had slow queries, and clients were polling for scores. I fixed both while the system stayed online.

Problem

The user base had grown faster than the schema. The busiest queries were doing full scans, and every client was polling for a scoreboard that changes all the time.

What I built

  • Normalised the schemas, added B-tree and composite indexes, and rewrote the slowest queries.
  • Shipped every change as a zero-downtime migration.
  • Moved the scoreboard to a Redis sorted set, where each write is O(log N).
  • Pushed updates over WebSockets, with ping checks that drop dead connections.

Applied research09

RAG vs fine-tuning on the same questions

I tried both approaches on the same HR policy questions. RAG answered 10 out of 10 correctly with no training. Then I fine-tuned TinyLlama-1.1B with LoRA on a free T4, training only 0.2% of the parameters. The loss went from 1.82 to 0.99, but the answers were still worse than RAG. My takeaway was to use RAG for questions about documents and keep fine-tuning for changing how a model behaves or writes.

Deep dive

How a pull request goes through the pipeline

This is the first project above, drawn as a diagram. Three models review the change separately. If any one of them asks for fixes, the change goes to the auto-fix step and is reviewed again before the tests run.

  • Every session starts fresh Each agent session starts with no memory of earlier ones. The context is rebuilt from the ticket, the project's rule files and the diff, so an earlier attempt can't influence a later review.
  • Only the tools each step needs Review sessions can only read files. The fix session can write and edit but can't run shell commands. The visual review is read-only and works from screenshots.
  • The fix loop has a limit Auto-fix runs twice at most. It also stops if there was nothing to commit or the push failed. After that the PR goes to a person.
